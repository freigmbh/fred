How to run and operate the AI review stack

How-to. Use a controller on your own machine. Local Docker checks capture GitLab effects; real GitLab acceptance uses a dedicated fixture project. You need Docker, Node 22.9 or newer, pnpm, and jq. Convex is self-hosted; no cloud login is used.

To run all of FRED on one server, use Deploy FRED with Docker. To investigate a deployed review, use Investigate a failed, stalled, or missing review; for spend, View monthly spend.

Verify changes in local Docker

Use this workflow to verify the current checkout without deploying to fred. Start Docker with Linux containers, then run:

pnpm fred dev verify

The command installs dependencies in Docker, starts an isolated Convex backend, connects its fixture project, and checks one FRED review with simulated model responses. It reports assertions, captured comments, and the source hash. Services started by this command stop when it finishes.

To keep a development instance running for repeated investigation:

pnpm fred dev up
pnpm fred dev verify --scenario provider-failure
pnpm fred dev inspect --json
pnpm fred dev logs

Open the dashboard URL printed by up. Use the printed controller URL and the key from the private admin-key file named in that output. Each worktree has its own instance and ports. After editing code, run up or verify again to rebuild the source snapshot.

To work on the admin UI against that instance, run the adminUi command printed by up, then open the Vite URL and log in with the secret from the private admin-secret file named in that output. The instance is seeded with a month of sample reviews, usage, and failures on fixtures/sample, a project verification never touches. Inspection output excludes its sample jobs, findings, and usage.

After an OpenRouter adapter change, put OPENROUTER_API_TOKEN in your host environment, root .env.dev, or apps/worker/.env, then run:

pnpm fred dev verify --live openrouter

To select a model and reasoning effort for both fixture stages, pass explicit overrides:

pnpm fred dev verify --live openrouter --model anthropic/claude-fable-5.1 --effort high

Agents may run these explicit local checks. They spend provider budget and capture comments locally. A pass requires both review stages and the known fixture defect. Real GitLab checkout, webhook delivery, and accepted MR comments still need the dedicated fixture-project procedure below. A passing local check does not prove those integrations.

To verify a large review through both model stages and captured publication, run the synthetic scenario first, then the live adapter:

pnpm fred dev verify --scenario large-diff
pnpm fred dev verify --scenario large-diff --live openrouter

This scenario generates 653 changed entries with long nested paths and more than 17 MB of diff text. Its manifest exceeds the inline budget. It requires both stages to read the complete paged catalog, follow diff continuation cursors and confirm the zero-input and deleted-module defects. Read the reported prompt sizes, assertions, and source hash. Checkout and GitLab publication remain simulated; the live command spends OpenRouter budget.

To remove the local containers while retaining their database and captured results:

pnpm fred dev down

To discard the instance entirely, or to sweep instances left by deleted worktrees, use the cleanup procedure.

If a command was forcibly killed and reports an existing lock directory, confirm the recorded process has exited before removing that directory. Use the source hash in verification output when reporting what was tested. See the local development reference for isolation, credentials, and coverage limits.

Deploy FRED with Docker

The Docker stack runs the backend, controller, worker, dashboard, and admin UI on one server with Docker Compose. You need Docker with Compose 2.20 or newer, a checkout of the release to run, and a hostname GitLab can reach over the company network.

  1. Create the configuration next to the compose file and keep it private: 
    cd docker
cp .env.example .env
chmod 600 .env
  2. Set FRED_PUBLIC_URL, FRED_DASHBOARD_URL, GITLAB_URL, and OPENROUTER_API_TOKEN. Fill INSTANCE_SECRET, WORKER_SECRET, ADMIN_SECRET, and GITLAB_WEBHOOK_SECRET with separate openssl rand -hex 32 values. Keep INSTANCE_SECRET for as long as you keep the database. Choose the worker mode: fixture with WORKER_FIXTURE_PROJECT_IDS and AI_REVIEW_LIVE=1 for named projects, or service for every connected project.
  3. For HTTPS, put the certificate chain and private key into docker/tls/ as tls.crt and tls.key, or point FRED_TLS_DIR at a directory holding them. The web server reads them as user and group 101, so give that group access without opening the key to other users: 
    sudo chgrp -R 101 tls
sudo chmod 750 tls
sudo chmod 640 tls/tls.crt tls/tls.key
    Copy the files rather than linking them: the container sees only this directory, so a link to certbot's live/ directory points nowhere and the web server refuses to start. Without them, the stack serves plain HTTP for an existing TLS proxy in front of it.
  4. Optionally set FRED_VERSION to the output of pnpm --silent fred --version, so reviews, usage, and the admin UI carry the version. Then build and start: 
    docker compose build
docker compose up -d --wait
    up returns once the deploy job has configured the controller and the worker, dashboard, and web server are running.
  5. Open FRED_PUBLIC_URL and log in with ADMIN_SECRET. A new controller starts with reviews switched off.
  6. Open FRED_DASHBOARD_URL and log in with the deployment URL, which is FRED_PUBLIC_URL, and the admin key from: 
    docker compose exec backend ./generate_admin_key.sh
    In Data > settings, set globalEnabled to true when the deployment is ready for reviews.
  7. Connect each project and add its webhook with the GitLab setup. The webhook URL is FRED_PUBLIC_URL followed by /api/webhook/gitlab.

To upgrade or roll back, check out the release, update FRED_VERSION, and run:

docker compose build
docker compose stop worker
docker compose up -d --wait

Stopping the worker first drains running reviews, for up to two hours, before the deploy job replaces the controller functions. Without it, the old worker keeps claiming reviews while the new functions deploy, and a contract change between the versions fails those reviews. Rolling back deploys the older functions; the database is never restored, and an incompatible schema change needs operator intervention.

To read logs, run docker compose logs -f worker, or name another service. To run the controller's Convex CLI, for example to enable maintenance mode, use the deploy service:

docker compose run --rm --no-deps deploy convex env set FRED_MAINTENANCE_MODE true

The deploy job resets WORKER_SECRET, ADMIN_SECRET, GITLAB_WEBHOOK_SECRET, GITLAB_URL, and BOT_USER_IDS_OTHER to their .env values on every up, so change or rotate those in .env, not with convex env set.

The backend-data volume holds the database, stored files such as transcripts, sealed project tokens, and the controller's FRED_TOKEN_KEY. Back it up together with .env; the volume alone cannot be opened without INSTANCE_SECRET. Keep backups private and outside the checkout, where image builds never read them. Stop the stack for a consistent copy:

mkdir -p -m 700 ~/fred-backups
docker compose stop
docker run --rm -v fred_backend-data:/data:ro -v ~/fred-backups:/backup -e OWNER="$(id -u):$(id -g)" alpine \
  sh -c 'umask 077 && tar -czf /backup/fred-backend-data.tgz -C /data . && chown "$OWNER" /backup/fred-backend-data.tgz'
docker compose up -d --wait

docker compose down removes containers and keeps the volumes. docker compose down --volumes deletes the database and the token key, so every stored project token and all review history are gone.

Clean up artifacts

Two places keep build and runtime leftovers past the command that created them.

ArtifactProcedure
Build output: apps/worker/dist, apps/ui/dist, and release.tar.gzpnpm clean. The next pnpm build recreates them.
Local Docker instances under ~/.local/share/fred-dev/, with their containers, volumes, and built imagespnpm fred dev clean. Removes this worktree's instance, including its database and captured results, and every instance whose recorded worktree no longer exists. Run it before deleting a worktree, or from any worktree to sweep orphans. An orphan still owned by a running command, or a state directory without recorded metadata, is left alone and reported as skipped.

CI release archives expire after seven days. Review checkouts, e2e backends, and their temporary directories are scoped resources their command removes on exit. After a forced kill, remove fred-review-* and fred-e2e-* directories in the system temporary directory and any fred-e2e-* container by hand.

Switch a project's review models

  1. Log in to the intended FRED admin UI and open Projects. Select the project and open its Review tab.
  2. Click Refresh under the panes to load OpenRouter's current compatible models.
  3. Select the model and effort for detection and validation.
  4. Click Save, which appears once a selection changed.

Newly queued reviews in that project use the saved pipeline. Queued and running reviews keep theirs. To abandon unsaved edits, click Discard. If another session saved first, the save is rejected; reload the project and choose again. The available combinations are listed in the pipeline reference.

Enable maintenance mode

In the intended self-hosted Convex dashboard, open Settings > Environment Variables and set FRED_MAINTENANCE_MODE to true. The controller must have the maintenance gate deployed.

To use the CLI, first check that apps/controller/.env.local targets the intended self-hosted deployment. From the repository root, run:

pnpm --filter @fred/controller convex env set FRED_MAINTENANCE_MODE true

FRED declines new requests with this comment:

AI review not run: FRED is currently under maintenance. Please request a review again once maintenance is complete.

Queued analysis gets the same denial at its next claim. Running reviews and saved publication continue. The controller delivers denial comments even when the worker is stopped.

To end maintenance, delete the variable in the dashboard or run:

pnpm --filter @fred/controller convex env set FRED_MAINTENANCE_MODE false

To delete the variable through the CLI:

pnpm --filter @fred/controller convex env remove FRED_MAINTENANCE_MODE

Ask reviewers to remove and re-add 0 FRED after maintenance. Native re-requests also work on supported GitLab versions. Denied requests do not restart automatically.

Configure the stack with the wizard

From the repository root, install dependencies and start the interactive wizard:

pnpm install
pnpm run setup

Use pnpm run setup. The shorter pnpm setup invokes pnpm's own installer.

The wizard covers the backend target, controller connection, GitLab, OpenRouter token, review settings, and saving. Each prompt explains its purpose and whether it is required or optional. Press Enter to keep a saved value. For optional fields, enter - to clear the value or restore the displayed default.

Choose existing for a self-hosted controller that is already running. Choose local to prepare the Docker backend configuration. The local path asks you to start the backend and generate its admin key in a second terminal before continuing. Keep the existing instance secret when using an existing database.

Allow the read-only controller check to reuse existing runtime values, especially shared secrets and FRED_TOKEN_KEY. The wizard generates FRED_TOKEN_KEY only when none is saved. Applying refuses to replace a different key already on the controller, because every stored project token would become unreadable. The wizard asks for no GitLab token. It explains the remaining GitLab steps: connect each project's 0 FRED project access token on the admin Projects page, then add its project webhook with Merge request events and Comments. See the GitLab setup. Provider billing is verified during the supervised pilot.

The wizard previews the output files and hides secrets. It writes owner-only env files and retains unrelated variables. Applying controller runtime values is a separate confirmation naming the target deployment; the wizard reads the values back to verify the update. It does not deploy functions, start services, call models, or start reviews.

For a new controller, the closing stage opens the dashboard and provides the initial settings row. Copy it only when no row exists. It starts with globalEnabled: false. The wizard does not change existing policy rows. If you skip applying controller variables or enabling fixture startup, the closing summary names those remaining steps. Rerun the wizard to apply saved values later.

Copy the worker configuration securely to the service account on the intended worker host. Choose each project's models in the admin UI when connecting it. Configuration is stored in:

  • apps/controller/self-hosted/.env for a local Docker backend.
  • apps/controller/.env.local for deployment URL and admin key.
  • apps/controller/.env.runtime as the local copy of controller runtime variables.
  • apps/worker/.env for the worker.

Run pnpm run test:setup for the offline setup checks. These checks also run under pnpm test. The manual steps below remain available when configuring a component separately.

Start the self-hosted Convex backend

  1. Create the env file next to the compose file and set the instance secret: 
    cd apps/controller/self-hosted
cp .env.example .env
INSTANCE_SECRET=$(openssl rand -hex 32)
awk -v secret="$INSTANCE_SECRET" '/^INSTANCE_SECRET=/ {$0="INSTANCE_SECRET=" secret} {print}' .env > .env.tmp
mv .env.tmp .env
    .env is gitignored. Keep REV pinned to the tag written in the template. Image tags on ghcr.io are full commit shas of convex-backend, not the precompiled-* release names on GitHub. To move to a newer build, pick a commit on main that has an image for both the backend and the dashboard. Not every dashboard image at a sha boots; DASHBOARD_REV overrides the dashboard tag alone and defaults to REV. Leave POSTGRES_URL empty. The MVP uses SQLite on the Docker volume.
  2. Start the backend and the dashboard. The first pull is about a gigabyte: 
    docker compose up -d
docker compose ps
    The backend listens on 3210 for clients and 3211 for HTTP actions and shows healthy in ps. The dashboard listens on 6791.
  3. Generate an admin key and write it into the controller's env file: 
    KEY=$(docker compose exec -T backend ./generate_admin_key.sh | tail -1)
printf 'CONVEX_SELF_HOSTED_URL=http://127.0.0.1:3210\nCONVEX_SELF_HOSTED_ADMIN_KEY=%s\n' "$KEY" > ../.env.local
    Every pnpm convex command below reads apps/controller/.env.local. That file is gitignored. Never point it at a shared deployment from a laptop.

If you see an error that mentions Convex Pro, the concurrency knobs are too low. The env template sets all four APPLICATION_MAX_CONCURRENT_* values to 64. Check they survived the copy.

Deploy the controller

  1. Install and check the workspace from the repo root: 
    pnpm install
pnpm -r typecheck
pnpm test
  2. Deploy the functions: 
    cd apps/controller
pnpm convex deploy -y
    Repeat this after every change to apps/controller/convex/. Use pnpm convex dev instead to redeploy on save. Note that pnpm convex codegen also pushes functions when .env.local names a reachable deployment.
  3. Set the controller's environment on the deployment. Pick a webhook secret and keep it, the replay step needs it: 
    SECRET=$(openssl rand -hex 16)
echo "GITLAB_WEBHOOK_SECRET=$SECRET" >> .env.local
pnpm convex env set GITLAB_WEBHOOK_SECRET "$SECRET"
pnpm convex env set GITLAB_URL https://gitlab.example.com
pnpm convex env set BOT_USER_IDS_OTHER 300
pnpm convex env set FRED_TOKEN_KEY "$(openssl rand -base64 32)"
WORKER_SECRET=$(openssl rand -hex 32)
printf 'WORKER_SECRET=%s\n' "$WORKER_SECRET" >> .env.local
pnpm convex env set WORKER_SECRET "$WORKER_SECRET"
    User 300 matches the Renovate-style author in fixtures/webhooks/. Set FRED_TOKEN_KEY once and keep it with the database; a new key makes every stored project token unreadable. GitLab tokens are not environment variables: connect each project with its 0 FRED token in the admin UI. Without a connected project, merge request webhooks are ignored, comment delivery is recorded as failed in mrNotes, and command verification fails without changing a finding.
  4. Insert the single settings row: 
    printf '{"globalEnabled":true,"defaultBudgetUsd":3000,"orgTimezone":"Europe/Berlin"}\n' > /tmp/settings.jsonl
pnpm convex import --table settings --format jsonLines -y /tmp/settings.jsonl
    Every webhook and every claim fails loudly until this row exists. To flip the kill switch later, edit the row in the dashboard or import again with --replace. The import command sometimes hangs after printing that it added the document; Ctrl-C is safe at that point.
  5. Open the dashboard at http://127.0.0.1:6791. It asks for the deployment URL, http://127.0.0.1:3210, and the admin key from .env.local. Confirm the tables from the schema exist. Port 3210 itself is the API and has no page.

Replay a webhook without GitLab

This is the controller path on your machine: token check, project lookup, trigger detection, dedupe, policy, enqueue. Most webhook fixtures are hand-written; reviewer-added-gitlab-18.0.json is a scrubbed real delivery. They target GitLab project 7 with user 901 as its 0 FRED bot. Connecting needs a real project access token, so on a stack without a connected project 7 every merge request fixture returns {"ignored":true,"reason":"project not connected to FRED"}. Use pnpm fred dev verify, which connects its own fixture project, to exercise the queue and worker without GitLab.

cd apps/controller
SECRET=$(grep GITLAB_WEBHOOK_SECRET .env.local | cut -d= -f2)
post() { curl -s -X POST http://127.0.0.1:3211/webhook/gitlab -H "X-Gitlab-Token: $SECRET" -H "Content-Type: application/json" --data @"$1"; echo; }

post ../../fixtures/webhooks/reviewer-added.json
post ../../fixtures/webhooks/duplicate-delivery.json
post ../../fixtures/webhooks/push-while-assigned.json
post ../../fixtures/webhooks/comment-only.json

Then look at the queue the way the worker does, and claim a job by hand:

WORKER_SECRET=$(grep '^WORKER_SECRET=' .env.local | cut -d= -f2-)
ARGS=$(jq -cn --arg workerSecret "$WORKER_SECRET" '{workerSecret:$workerSecret,providers:["fred"],workerId:"manual-local-check"}')
pnpm convex run jobs:listQueued "$(printf '%s' "$ARGS" | jq 'del(.workerId)')"
pnpm convex run jobs:claim "$ARGS"
pnpm convex data reviewJobs

The claimed job is running with claimedAt, leaseToken, and leaseExpiresAt set. A manual claim without heartbeats expires and produces a failure comment delivery. A wrong webhook token gets 401. Worker calls with an invalid secret are rejected. Webhook delivery dedupe rejects replay. Use a fresh delivery and head SHA for another push case, or a fresh deliberate re-request for another attempt at the same SHA.

To see a denial, set globalEnabled to false, replay a fixture with a fresh sha, and read the response. The job is not inserted. Read pnpm convex data mrNotes for the denial comment and delivery status. With placeholder GitLab configuration, delivery fails as expected.

After fixing a failed comment delivery, retry its existing mrNotes row from the dashboard or CLI:

pnpm convex run mrNotes:retryFailed '{"noteId":"<mrNotes document id>"}'

Reset

To start from an empty database without redeploying, clear the tables from the dashboard. To wipe everything including the admin key:

cd apps/controller/self-hosted
docker compose down -v

Then repeat the admin key step, deploy, and set the environment again.

Expose the webhook to GitLab

GitLab must reach port 3211 on your machine. If GitLab runs on the company network and your machine is on it, use your machine's address. Otherwise open a tunnel that stays inside the company network and point the fixture project webhook at it. Do not use a public tunnel service.

Once a real delivery has arrived, save its body from the webhook's recent deliveries page into fixtures/webhooks/ next to the hand-written ones. The trigger detection depends on the exact shape of changes.reviewers, and the hand-written fixtures are a guess until then.

Prepare a human-run fixture review

Use a local self-hosted Convex backend and the Node worker. This procedure spends OpenRouter budget and posts real GitLab comments, so it requires explicit fixture-project authorization.

  1. Use a dedicated fixture project on the company GitLab instance. Create an MR with a small known defect, root REVIEW.md, and a referenced repo SKILL.md. Create its 0 FRED token, connect it in the local admin UI with ADMIN_SECRET set as in Open the admin UI, and configure its project webhook with the GitLab setup guide.
  2. Keep CONVEX_URL on your machine and configure WORKER_SECRET and FRED_TOKEN_KEY on that local controller. Point only the fixture project's webhook at that controller.
  3. Copy apps/worker/.env.example to apps/worker/.env. Fill the values for this human-run check. The start command loads that optional file; already exported environment values take precedence: 
    CONVEX_URL=http://127.0.0.1:3210
WORKER_MODE=fixture
WORKER_FIXTURE_PROJECT_IDS=<fixture project numeric ID>
AI_REVIEW_LIVE=1
WORKER_SECRET=<the local controller's worker secret>
GITLAB_URL=https://<internal GitLab host>
OPENROUTER_API_TOKEN=<service OpenRouter token>
WORKER_CONCURRENCY=8
    The worker receives each project's token with its claim; its environment holds no GitLab token. Keep values out of Git. Fixture mode restricts the controller and project targets; it still spends real provider budget and posts as the project's FRED bot.
  4. Start the worker from the repo root: 
    pnpm --filter @fred/worker start
    The worker logs FRED worker connected and waiting for reviews. Keep service mode and the shared controller out of this local pilot.

Verify FRED on GitLab

Select the models to exercise in the fixture project's pipeline on the admin Projects page. Use only the fixture MR and keep AI_REVIEW_LIVE=1 set.

  1. Add 0 FRED as reviewer. Confirm the worker claims the expected fixture project and SHA.
  2. Check that the review follows root REVIEW.md and loads the referenced repo skill. Repeat with a missing skill and with no REVIEW.md; expect a hint and a feature tip respectively.
  3. Include instructions that request a shell command, a write, and a host file outside the checkout. Verify that the worker exposes only its controlled tools and that worker credentials are unavailable. Stop the pilot if any forbidden capability succeeds.
  4. Confirm that the summary contains every accepted finding and nit, actionable findings use valid inline locations, and FRED sets its fred-review:: label. Check a review with no new findings and an earlier open actionable finding. Expect its remaining count and link in the summary, and fred-review::findings.
  5. Check reviewJobs, findings, and usageEvents in the local dashboard. Expect a saved result before publication, ordered acknowledgements, every finding status retained, and usage deltas with stable event keys. Investigate usageIncomplete; missing observations are not proof of zero cost.
  6. Interrupt an analysis and re-request it deliberately after the failure. Interrupt publication after the summary and restart the worker. Expect publication recovery without another model run or duplicate summary.
  7. On the fixture project, push another commit during a review. Verify that outdated results remain stored, detected outdated work stops further publication, and the queued review handles the new head.
  8. Temporarily stop the local controller. Verify that claims and publication pause, active analysis stops after bounded reconnection attempts, and the worker remains alive. Restore the controller and verify interruption reporting and saved-publication recovery.

Record the SDK version, requested and resolved models, observed tool availability, GitLab result, and usage behavior. Follow the fixture recording instructions before saving responses. Synthetic tests alone do not establish these live properties.

Verify finding decisions on a fixture MR

Use an existing review on the dedicated fixture MR and the local controller. This procedure posts real GitLab comments and requires explicit fixture-project authorization. The command itself makes no model call. Use a published FRED finding; commands on findings of the retired Claude and Codex bots are rejected.

  1. Enable Comments on the fixture project's existing webhook. Keep Merge request events enabled.
  2. As the MR author or a project Maintainer, copy the finding reference from its summary or inline comment. Post one plain line: 
    fred dismiss <finding-ref> The behavior is intentional.
    Replace <finding-ref> with the published reference. Do not wrap the command in backticks or add another line.
  3. Wait for the worker to finish any active work on that MR. Check for the dismissal reply, its reason, and its decision reference. If the finding has an inline discussion, expect that discussion to resolve. Summary-only findings receive a separate decision comment.
  4. Check findingCommandRequests, findingCommands, and findingDecisions in the local dashboard. Expect a completed command and one human decision tied to the source note. The finding remains posted with dismissed disposition. Expect no new review, usage row, or reviewed SHA.
  5. Check the FRED label. If another open blocking or should-fix finding remains, expect fred-review::findings. Otherwise expect fred-review::clean, including when only nits remain.
  6. Copy the decision reference from the dismissal reply and post: 
    fred undo <decision-ref> The requirement still applies.
    Expect a new audit row, open disposition, and an open inline discussion when one exists. The earlier decision remains stored.
  7. Edit or delete an already accepted command comment. Confirm that the finding's disposition does not change. Resolve its GitLab discussion manually and confirm that its disposition and FRED label remain unchanged.
  8. For a validator retraction, check the evidence and decision reference in the next review summary. Undo that current retraction to verify the same reopen behavior. A code fix remains fixed and is ineligible for undo.

If a command produces no reply, inspect its note webhook delivery and stored receipt. An ignored delivery can be an edited note, a bot or system note, invalid command syntax, or an unknown project. Verification fails when the project is not connected. Use a new comment for a corrected command.

The webhook acknowledges a stored receipt before GitLab verification begins. If verification fails, inspect findingCommandRequests and its durable failure note. Correct the configuration or availability problem and submit a new command after retries are exhausted.

If publication fails, inspect the command's saved result, acknowledgements, and failure comment. Any accepted decision remains in effect. After bounded recovery is exhausted, the next review recalculates its label from current dispositions. See the command reference for states and limits.

Test concurrent reviews offline

Run pnpm test:e2e with Docker available. The command creates a disposable self-hosted backend, deploys the controller with test-only internal fixtures in a temporary directory, and removes the container afterward. The disposable SQLite database lives in container memory. The checks exercise real transactions, not disk durability. They use synthetic provider and GitLab service layers, never provider credentials or real MRs.

The command sets a fresh FRED_TOKEN_KEY and connects fixture project 1 through e2e:connectFixture with a sealed token, so each claim proves the sealing round trip. The checks run reviews of four MRs with concurrent usage, diagnostics, heartbeats, and stale cleanup. They also exercise webhook replay, failed-analysis retries, and saved-publication recovery. CI runs the checks against a disposable GitLab service with public fixture credentials; it requires no privileged Docker daemon. These tests establish controller and worker behavior. Use the local live verifier for OpenRouter and the authorized fixture project for real GitLab acceptance.

Investigate a failed, stalled, or missing review

Run these commands in docker/ on the server of a Docker deployment. They read state and change nothing. Never print or paste .env or the admin key.

  1. Check the services and the deployed version: 
    docker compose ps
grep FRED_VERSION .env
  2. Get the controller’s record. A failure comment on the MR names the job ID. Select a job, an MR, or recent work: 
    docker compose run --rm --no-deps deploy convex run diagnostics:inspect '{"jobId":"<job ID>"}'
docker compose run --rm --no-deps deploy convex run diagnostics:inspect '{"projectPath":"group/project","mrIid":42,"provider":"fred"}'
docker compose run --rm --no-deps deploy convex run diagnostics:inspect '{}'
  3. A failure reason that names a missing access token means the project was disconnected or its token cannot be opened; check FRED_TOKEN_KEY and the Projects page. Otherwise read the job’s snapshot.failure. The category and codes route the problem: authentication, invalid-request, transport, and output failures need different fixes. detail is the redacted cause chain. For a stall, compare snapshot.lastActivityAt with leaseExpiresAt and the event times. The controller holds no tool events, and its lastActivityAt can trail the worker by about 70 seconds; the worker log below has every tool event at its exact time. A heartbeat establishes worker ownership, not model progress.
  4. Read the worker’s timeline for the job. Every diagnostic event, and the failure with every stack, is one JSON line in the worker log: 
    docker compose logs --no-log-prefix --since 48h worker | grep '<job ID>' | jq -Rc 'fromjson? | .event // {failure, phase}'
docker compose logs --no-log-prefix --since 48h worker | grep '<job ID>' | jq -Rr 'fromjson? | select(.fredFailure) | .trace'
docker compose logs --no-log-prefix --tail 200 worker | grep -v fredDiagnostic
    fromjson? skips the readable warning lines that share the job ID. The last command shows startup, connection, claim, and failure warnings without the event stream.
  5. For controller errors, read Convex function logs and the backend log. logs streams until timeout ends it. 
    timeout 20 docker compose run --rm --no-deps deploy convex logs --history 200
docker compose logs --tail 200 backend
  6. For a missing job, read the MR report’s webhook_received and webhook_ignored events and their reasons. Reason unconfigured means the project is not connected; check its token on the admin Projects page. Then read the web server: docker compose logs --no-log-prefix web | grep webhook/gitlab | tail. noWebhookReceipt means no receipt in the retained scan, not that GitLab sent nothing. When both are empty, inspect the project’s webhook delivery history in GitLab. HTTP 401 indicates a missing or mismatched secret.
  7. For incomplete publication, compare publication.acknowledged and total with the publication events. Note rows show status, attempts, and the last GitLab delivery error. A saved result alone does not prove that GitLab received it; confirm the summary and label on the MR.
  8. For raw tables, use docker compose run --rm --no-deps deploy convex data <table> --limit 20 --order desc or the dashboard at FRED_DASHBOARD_URL.

The worker log keeps events the controller dropped; the controller keeps job snapshots, failure rows, and notes after detailed events expire at seven days. Read every coverage flag and narrow a truncated report to a job. Do not rerun a real MR review just to obtain evidence; use the local OpenRouter verifier for an isolated model check. See the diagnostic reference for what each record contains.

Backfill usage days

Usage rows written before the day column existed have no day bucket, so they are missing from the daily spend chart. Run this once per deployment after deploying a controller that has the column. It patches 500 rows per call; repeat until remaining is false. It changes no cost or token amount.

pnpm --filter @fred/controller convex run migrations:backfillUsageDay

Confirm apps/controller/.env.local targets the intended self-hosted deployment first. Once every deployment reports remaining: false, the column becomes required in the schema in a follow-up change.

Backfill usage rollups

The spend page and the budget gate read usageDaily and usageMonthly, which recordUsage fills for every row written since the deploy that introduced them. Older ledger rows are missing from both until this runs, so spend under-reports and budgets look fresher than they are. Run it once per deployment right after that deploy. It folds 200 rows per call, oldest first, marks each row rolledUp, and skips rows already marked; repeat until remaining is false. Rerunning or resuming after an interruption adds nothing twice. It changes no ledger amount.

pnpm --filter @fred/controller convex run migrations:backfillUsageRollups

Confirm apps/controller/.env.local targets the intended self-hosted deployment first. The worker can keep running. Rows without a day get one from their creation time, so backfilling usage days first is not required. Afterwards compare the spend page's month total with the ledger query; they agree to within half a micro-dollar per ledger row, well under a cent, since the rollup rounds each row to the micro-dollar before summing.

Backfill review outcomes

The overview's outcome table reads reviewOutcomes, which jobs.complete fills for every review completed since the deploy that introduced it. Earlier done reviews are missing until this runs, so the month's done count, clean labels, findings, and latency under-report. Run it once per deployment right after that deploy. It writes the rows of 10 done jobs per call, oldest first, so a call stays under the read limit even when saved results are near the 1 MiB document limit, and returns a cursor; pass it back until remaining is false. The loop below does that and stops on the first failed call. Jobs that already have a row are skipped, so rerunning or resuming adds nothing twice. It changes no job or finding.

args='{}'; while out=$(pnpm --silent --filter @fred/controller convex run migrations:backfillReviewOutcomes "$args"); do
  echo "$out"; [ "$(jq -r .remaining <<<"$out")" = true ] || break; args=$(jq -c '{cursor}' <<<"$out")
done

Confirm apps/controller/.env.local targets the intended self-hosted deployment first. The worker can keep running. The overview shows the month's earlier reviews once the loop ends with remaining: false.

Backfill legacy finding dispositions

Run this explicit migration after deploying a controller with migrations.backfillFindingDisposition. Test it on your local instance first. On a shared deployment, an authorized operator runs the migration during a maintenance window.

  1. Confirm that apps/controller/.env.local names the intended self-hosted URL and admin key. Do not use a Convex Cloud target.
  2. Pause the worker and let its current work finish. Maintenance mode alone does not stop finding commands.
  3. From the repository root, run: 
    pnpm --filter @fred/controller convex run migrations:backfillFindingDisposition
    Each call processes at most 500 matching findings. Repeat until remaining is false.
  4. Inspect the migrated rows. Legacy posted findings have open disposition. Legacy resolved findings become posted with fixed disposition and a decision whose source is migration. Its reason states that original decision metadata is unavailable.
  5. Check that saved reviewJobs.resultJson values remain unchanged. Resume the worker.

The migration records its own provenance. It does not reconstruct the original actor or decision time. Historical result decoding remains available without changing old publication effects or markers.

Open the admin UI

Set the read credential on the controller once. Confirm apps/controller/.env.local targets the intended deployment, then run:

pnpm --filter @fred/controller convex env set ADMIN_SECRET <random 32 byte hex>

Open the admin UI, FRED_PUBLIC_URL on the Docker stack, and enter that secret. The browser keeps it until you log out or the controller rejects it. Queue shows every job in flight in one table per stage, queued, running, and publishing, with ticking ages, the worker phase, and publication progress, and marks a lease past due, a running review with no provider activity, and a recovered publication. Spend shows the selected month per day and lab, the working-day burn rate, and the month's breakdown per model and per budget owner. Collect stage transcripts

Transcript collection stores each review stage's full model conversation for later evaluation. It is off by default and switched per project. A transcript contains the source code, diffs, and MR discussions the agent read. Tell the project's team before you switch it on. Deleting is a Convex write; on a shared deployment it needs operator authorization.

  1. Open the project on the admin UI's Projects page. Connecting creates its projects row.
  2. On its Review tab, under Transcripts, choose Collect, then Confirm collect. Without the admin UI, open Functions in the intended self-hosted Convex dashboard, select transcripts:setCollection, and run it with the project path and enabled. On the Docker stack, the deploy service does the same: 
    docker compose run --rm --no-deps deploy convex run transcripts:setCollection '{"projectPath":"group/project","enabled":true}'
    For another deployment, confirm apps/controller/.env.local targets it, then use pnpm --filter @fred/controller convex run with the same arguments.
  3. Reviews queued after the switch collect. Queued and running reviews keep the setting they were queued with. Choose Stop, or run the same function with "enabled":false, to stop collecting; already queued collecting jobs still store their transcripts.
  4. To download, open Reviews in the admin UI and expand the review. Each stage attempt lists its outcome, model, size, and turns with a download. The file is gzipped JSON; read it with gunzip -c fred-*.json.gz | jq.
Expanded review showsMeaning

None recordedThe job collects, but no stage reached its first model request, or the store failed. A failed store leaves a warning in the worker journal.

Transcripts remain until deleted. To delete one job's transcripts, or every transcript of an MR:

Export all data

The admin UI downloads everything the controller stores as one zip. The archive holds source code from reviewed MRs and developer names, usernames, and GitLab IDs, so keep it where you would keep the repositories.

  1. Open Export in the admin UI and choose Export all data. Keep the tab open: leaving the page asks first, then cancels the export and discards what it read.
  2. The page reads each table page by page, then downloads the transcript files four at a time, and shows each table's rows, size, and status. When it finishes, the browser saves fred-export-YYYY-MM-DD-HHmm.zip, named by the local start time. Save again downloads the same archive; Start over returns to the start.
  3. Each request is tried 3 times. After that the export stops, keeps what it read in the tab, and offers Retry from the table or the transcript files where it stopped, or Discard. A rejected admin secret logs out. Cancel discards the export.
manifest.json              formatVersion fred-export/1, fredVersion, exportedAt, rows per table, transcript file count, notes
tables/<table>.jsonl       one stored document per line, with _id and _creationTime
transcripts/<id>.json.gz   one file per available transcript, named by its transcripts row _id, stored as gzip

Rows join on _id. Sealed project tokens, lease tokens, and storage IDs are left out, and webhookDeliveries is not exported. The browser reads each table page by page and each transcript file separately, so rows written during the export may or may not appear: the archive is not a point-in-time snapshot. A transcript file deleted after its row was read is left out and counted on the page. When no table has a row, the page says there is nothing to export instead of saving a zip. Read a transcript with unzip -p fred-export-*.zip transcripts/<id>.json.gz | gunzip | jq. See the admin API for the exported fields and page sizes.

View monthly spend

The admin UI above is the first stop. The query below sums the ledger directly and is the fallback when the UI is unavailable, and the cross-check for the usageMonthly rollup the server reads.

  1. Log in to the self-hosted Convex dashboard and open Data.
  2. Open the menu next to a table and choose Custom query.
  3. Paste this entire module, including export default query. Set month to the stored calendar month you want, then run the query: 
    export default query({
	handler: async (ctx) => {
		const month = "2026-09";
		const developers = await ctx.db.query("developers").collect();
		return await Promise.all(developers.map(async (developer) => {
			const rows = await ctx.db.query("usageEvents")
				.withIndex("by_developer_month", (q) =>
					q.eq("developerId", developer._id).eq("month", month))
				.collect();
			return {
				user: developer.username ?? developer.gitlabUserId,
				gitlabUserId: developer.gitlabUserId,
				month,
				spentUsd: Number(rows.reduce((sum, row) => sum + row.costUsd, 0).toFixed(4)),
			};
		}));
	},
});

A developer with no usage in that month returns zero. An empty developer table returns an empty list. A top-level return without the wrapper causes Illegal return statement. Treat the result as recorded estimated spend, subject to the usage limits. The query changes no data and requires no software deployment.
