Triggers

Each participating project has its own webhook from the same GitLab instance. All project webhooks use the same endpoint and secret and send merge request and comment events. Each project reviews through its own FRED bot: the bot user GitLab creates for the project's 0 FRED project access token. Only a connected project, one with a stored token and a review pipeline, can trigger a review. A group webhook sends the same payload, and the controller does not distinguish it from a project delivery.

GitLab 18.0 sends changes.reviewers as { previous, current } without state or re_requested on the entries. GitLab 19 sends [previous, current] with both. The controller parses both shapes. Re-request detection needs GitLab 19; on 18.0 a re-request is not a webhook event at all.

The webhook reads the project's FRED bot through projectTokens.identity. detectTrigger(event, botId, botAuthorIds) returns at most one trigger per delivery, so one delivery creates at most one job. A bot-authored MR is one whose author is any FRED bot user of any project, including former bot users of replaced tokens, or a user in BOT_USER_IDS_OTHER. Such an MR triggers only when a human adds or re-requests the FRED bot.

The review identity is projectId + mrIid + headSha + provider. Webhook delivery keys prevent duplicate deliveries from creating another attempt. A fresh deliberate re-request can create a new attempt at the same head SHA when no matching work is outstanding. Duplicate deliveries leave queued jobs unchanged, including replays of an older push. The budget owner for a job on a bot-authored MR is the user who added the reviewer.

Policy

Evaluated at enqueue and again at claim. First match wins. Every denial posts one comment on the MR as the project's FRED bot.

Maintenance mode applies to every provider and takes precedence over every other gate. Only the exact controller environment value FRED_MAINTENANCE_MODE=true enables it. An unset variable, false, or any other value leaves it off. New requests get a maintenance denial comment without a job. Queued analysis is denied at its next claim. Running analysis and saved publication continue. Clearing the flag does not restart denied work. A fresh review request passes through policy again. Delivery and review deduplication still apply.

The budget is a developer's budgets.monthlyUsd override when present, otherwise settings.defaultBudgetUsd, 3000 by default. Optional developer blocks and project provider policies already participate in the gate. A projectPolicies row is keyed by project and provider, so a row for fred governs that project's reviews. Spend this month is the developer's usageMonthly row for the month, one document read through by_developer_month, converted from micro-dollars. recordUsage maintains that rollup in the same transaction as the ledger insert, so it equals the sum of usageEvents.costUsd for the developer and the month once migrations.backfillUsageRollups has run. The month is stored on each event as yyyy-mm in the org timezone at write time.

A job that passes at enqueue and fails at claim is set to denied and gets the comment then.

There is no per-review cost cap. A running review is never stopped for budget reasons.

Every public worker operation requires workerSecret, compared with WORKER_SECRET without early exit. Mutations for a claimed job also require its current leaseToken. The controller rejects expired or replaced owners. The review agent receives neither credential.

jobs.claim claims an eligible finding command before review work. Otherwise it chooses the oldest eligible queued review or recoverable publication. Running and publishing FRED reviews and commands share exclusion for the same project and MR. Work of the retired bots never holds an MR. Different MRs run concurrently, up to WORKER_CONCURRENCY per worker. Review claims compute previousReviewedSha from the latest completed or skipped review for that MR and provider. Claims and the queue subscription cover only provider fred and ignore a providers argument; queued work of the retired claude and codex bots stays unclaimed until migrations:retireLegacyQueue retires it.

A claim returns the project's credential with the job: gitlabBotUserId, the bot user of the stored token; gitlabBotUserIds, every FRED bot user the project has had; and gitlabToken, the opened project access token. The claim is the only public function that returns a token, and it requires workerSecret and grants the lease in the same transaction. Queue and admin queries never return it. When the project has no token, or its sealed token cannot be opened, the claim fails the review with this reason and its failure comment, then moves to the next job:

FRED has no usable access token for this project. Connect the project in the FRED dashboard, then request the review again

A finding command in that state is marked failed with the same reason. Without a usable token the failure comment cannot be delivered either, so it is recorded as note_failed.

The queue subscription includes running and publishing lease expiry times so a restarted worker wakes when abandoned ownership expires. The worker renews its two-minute lease every 30 seconds, and again before each publication effect. Lost analysis expires as failed with reason stale. Remove/re-add starts both analysis stages in a new attempt. Lost publication remains recoverable. A reclaimed publication receives a new lease and resumes its stored effects without model calls.

The claim loop wakes at startup, on queue subscription errors, when a job finishes, at lease expiry, and when the WebSocket changes from disconnected to connected. A queue subscription update wakes it only when the update contains a queued review or command or an expired lease. Every update reschedules the lease-expiry wake, so an update that only renews a lease through a heartbeat does not claim. Other connection state changes, such as in-flight request counts or retry counts, do not wake the loop. A failed claim schedules a retry after ten seconds.

SIGTERM and SIGINT stop new claims and let active reviews finish before the worker exits. An in-flight claim is still completed and processed. The deployment service allows up to two hours for shutdown before systemd terminates the process.

Each model stage has a 45-minute timeout. There is no model-call or tool-call count limit. Checkout has a separate five-minute operational timeout. max_turns remains readable on historical rows but is not emitted by the worker.

Controller connection loss pauses claims and publication. The worker keeps running and allows a bounded reconnect window of 15 seconds before interrupting analysis. Essential job RPCs wait up to 15 seconds for the same in-flight request. Owned publication and heartbeat waits end at least one second before the last confirmed lease expiry. Timeouts do not cancel Convex mutations or create replacement requests. Claims retain their pending request until it settles so a granted lease is not abandoned. The worker attempts to record interrupted analysis within another bounded RPC wait; lease cleanup records abandoned analysis if that attempt fails. Confirmed lease loss stops the old owner without a failure write. Tagged application rejection fails immediately. Settled untagged errors receive at most two retries after 100 and 200 milliseconds within the original wait budget; exhaustion fails the job. Best-effort diagnostics do not retry settled errors. A single-host deployment shares one clock between worker and controller; owned-call budgets assume synchronized clocks. After a controller timeout, ambiguous save responses leave stored publication recoverable. Stored publication resumes under a valid lease.

OperationContract
jobs.saveResultValidates and stores all findings, finding decisions, and immutable publication effects before the first GitLab write. Records the current finding revision and moves the job to publishing.
jobs.ackPublicationAcknowledges effects in stored order. Repeated identical acknowledgements are idempotent. Summary acknowledgement marks accepted findings posted and records the summary note ID. Inline acknowledgement records discussion and note IDs. These delivery updates preserve disposition. A resolve acknowledgement applies its explicit validator decision and appends the audit row.
jobs.completeRequires every effect acknowledged. Applies remaining summary-only finding decisions and marks the job done. Already applied decisions are idempotent.
jobs.failPreserves stored results, records the failure, and queues its comment.
jobs.interruptAnalysisFails interrupted analysis. Leaves stored publication recoverable. Interrupted analysis records an accounting gap.
jobs.supersedeStops publication with an outdated head or finding revision while retaining stored findings and acknowledgements.
jobs.skipEnds running analysis whose incremental comparison was empty. Answers skipped: false and leaves the job running when a published open finding came from a review that never completed, because only a completed review validated its findings against the baseline tree. Rejects a job that already saved a result.

Validator decisions identify earlier findings from the same project, MR, and provider and carry the expected current decision ID. New decisions require a published, open finding. Invalid ownership or a changed decision rejects the result before publication. Historical fixed rows remain readable for recovery of legacy results.

A saved review's findingRevision identifies the latest decision for its MR and provider. The worker checks this revision before publication. The controller rejects stale resolution and label acknowledgements and stale completion. A newer decision prevents replay of obsolete resolution or label effects. Recovery reconciles an uncertain summary by marker and bot author before superseding the review. Decisions applied by the review advance its saved revision.

readReviewResult validates historical results containing resolvedFindingIds and decodes them as fixed decisions. It preserves the stored JSON, publication bodies, effect keys, and acknowledgements. It does not rewrite historical results.

Stale cleanup and claim-time expiry read at most 32 expired jobs per status through lease-expiry indexes, including legacy analysis deadlines. Healthy running jobs are outside those reads.

A fresh reviewer-add delivery can retry the latest failed or denied attempt at the same SHA. Failed or denied analysis creates a new job, preserving the earlier attempt. Failed publication queues the original job with its immutable result and acknowledgements, immediately revokes the old lease, and receives fresh ownership at claim. Enqueue policy applies before deliberate recovery, using the original budget owner for saved publication. Saved publication does not repeat analysis policy at claim, matching automatic publication recovery. All work on one MR still serializes.

A matching queued, running, or publishing attempt suppresses both reviewer-add and re-request duplicates. A fresh native re-request can rerun a completed review. Remove/re-add only bypasses same-SHA deduplication after failure or denial. Webhook delivery replay remains idempotent after failure and after policy changes. Publication verifies the current MR head before each effect and supersedes obsolete results.

Comment delivery

Denials and failures create an mrNotes row in the same transaction as their policy or job update. A failure uses job ID and lease generation as the delivery key. Its note row retains job association and the validated compact failure snapshot after recovery. Other job notes use the job ID. An enqueue denial uses project, MR, head SHA, provider, and denial reason. A finding command rejection uses project and note ID, a finding command failure adds its lease generation, and a verification failure uses the receipt ID. Repeated scheduling of a key creates no second delivery. noteKeys.ts builds every key.

StatusMeaning
pendingScheduled for its first attempt or a retry.
sentGitLab accepted the POST, or a retry found its marker in an existing note.
failedPermanent error or all five attempts exhausted. lastError records the cause.

Every note posts as the project's FRED bot through its stored token, including notes about jobs of the retired bots. Network errors, HTTP 408, HTTP 429, and HTTP 5xx retry after 5, 30, 120, and 300 seconds. Each HTTP request has a 10-second timeout and rejects redirects, so the token never leaves GITLAB_URL. Other HTTP errors, invalid configuration, and a project that is not connected fail without retry; the last records GitLab configuration invalid or project not connected. Before each delivery attempt, the controller searches all MR notes pages for the hidden fred-note marker. A match prevents another POST when the previous response was lost. The internal mrNotes.retryFailed mutation restarts a failed delivery with its original marker and resets the attempt count. This does not provide an atomic transaction with GitLab or recovery from a controller process crash during delivery.

diagnosticSnapshots holds each job’s worker snapshot: phase, timestamps, failure classification and detail, release, active stage model and effort, lease generation, and dropped-event count. Stored snapshots are bounded to 16,384 characters. The model and effort remain available after that stage completes. Job reports also include saved detection and validation selections with valid diagnostic model identifiers and recognized effort values, including models no longer in the catalog. The job’s diagnosticJson holds lifecycle outcomes and legacy snapshots. Reports combine both by lease generation; lifecycle mutations never read the worker snapshot. Compact snapshots remain with the job. A newer phase cannot erase an already recorded failure in the same lease generation. An expired or replaced owner cannot repair its diagnostics. Publication recovery starts a new lease generation.

diagnosticEvents holds validated metadata with recordedAt and expiresAt. Queries exclude events after seven days. A minute cron removes up to 500 expired rows per run, so physical deletion can lag during outages or a backlog. Findings, usage rows, publication records, and compact job outcomes do not expire with diagnostic events.

The worker buffers at most 128 events per job and flushes every ten seconds and once when the job ends. A flush sends batches of at most 25 in order until the buffer is empty or a batch fails. Each batch waits at most one second. Without buffered events, a flush sends the snapshot alone only when its dropped-event count changed, or when lastActivityAt moved and the previous send is at least a minute old; the final flush sends any moved activity. The stored lastActivityAt can therefore trail observed activity by about 70 seconds. One underlying diagnostic mutation can remain pending across all reviews in a worker; another starts only after that request settles. A periodic flush that finds this slot busy sends nothing and keeps its batch for the next flush. Overflow, failed or timed-out writes, and a final flush that finds the slot busy drop events from the controller. A final flush that stops at a failed batch also drops every event still buffered; the snapshot records observed drops. Controller recording is best-effort. Diagnostic failure does not fail a review; required accounting and publication writes retain their existing behavior.

The worker journal is the complete local timeline. Each diagnostic event is one JSON line, {"fredDiagnostic":1, jobId, gitlabProjectId, mrIid, headSha, provider, leaseGeneration, event}, written whether or not the controller accepts it, including tool events the controller never receives. Controller events keep their journal sequence, so tool events leave gaps there. Each job failure or interruption adds one {"fredFailure":1, …correlation, at, outcome, phase, failure, trace} line. Finding command failures write the same line with commandId. A worker stopped by a runtime failure writes {"fredRuntimeFailure":1, at, failure, trace} to stderr. Transcripts

Transcript collection is off by default and switched per project in projects.collectTranscripts. Enqueue copies it onto a new job as reviewJobs.collectTranscripts, like stageModels, and writes the field only when true. Job, lease generation, and stage identify it, so a retried job keeps every attempt. A stage that ends before its first model request stores nothing. Projects and tokens

Each project reviews through its own FRED bot. The admin creates a GitLab project access token in the project, names it 0 FRED so the bot sorts first in reviewer pickers, and pastes it on the admin Projects page. GitLab creates a bot user for every project access token; that bot user is FRED in the project. A project is connected when it has a stored token and a review pipeline. New jobs, findings, usage rows, failures, and notes use provider fred.

Token storage

projectTokens.sealedToken is AES-256-GCM ciphertext under the controller's FRED_TOKEN_KEY, 32 random bytes in base64, with a fresh 12-byte IV per seal. The GitLab project ID is authenticated data, so a sealed token opens only for its own project. Maintenance agents may read controller data, which is why the token is never stored in plain text. Only functions in projectTokens.ts open tokens, for the worker claim, MR note delivery, finding-command verification, and token checks. A changed or missing key makes every stored token unreadable; each project then needs its token pasted again.

Token lifecycle

The admin UI marks a token with a warning within 30 days of its expiry and as failed when it has expired or the last check recorded a problem. GitLab's Rotate keeps the same bot user; paste the new value with Replace. A brand-new token creates a new bot user. FRED appends that user to projects.botUserIds and keeps every former one, so discussions and summaries the old bot wrote still count as FRED's for resolution, reconciliation, and prompt filtering. Reviewer assignments of the old bot user no longer trigger reviews.

After a disconnect, new merge request webhooks for the project are ignored as not connected. Already queued reviews fail at claim, queued finding commands are marked failed, command verification fails as a configuration failure, and MR notes cannot be delivered. Connecting the project again reverses this for new requests; failed work needs a new request.

Retired bots

The provider keys claude and codex belong to the retired shared GitLab user accounts that reviewed before project access tokens. They remain in the schema so their jobs, findings, usage rows, failures, labels, and spend stay readable. The Reviews filter offers all bots. Overview always shows FRED and shows a retired bot only in a month in which it completed reviews. Retired bots never trigger, the worker claims only fred, and finding commands on their findings are rejected. A retired bot's running review fails when its lease expires. A retired bot's publishing job is never reclaimed and keeps its MR busy for every provider, so its publication must finish before the cutover.

Review pipelines

Each connected project has a review pipeline: a model and effort for the detection stage and for the validation stage, stored in projects.stageModels and chosen from the compatible OpenRouter catalog. The admin chooses it at first connect, prefilled with defaultStageModels, and edits it on the Projects page. Bot identity controls GitLab ownership, labels, and policy, not model vendor.

admin.refreshModels reads OpenRouter's public model catalog through the official SDK without credentials. A successful refresh replaces the stored catalog. A failed or empty refresh leaves the previous catalog intact. An older concurrent refresh cannot replace a newer snapshot. Eligible models have a valid OpenRouter ID, positive context length, text input and output, and tool support. Batch-only models are excluded. The stored metadata includes context length, maximum completion tokens, supported parameters, and reasoning options.

default omits a reasoning override. Explicit options are none, minimal, low, medium, high, xhigh, and max, filtered by each model's reasoning metadata. Models with mandatory reasoning exclude none. Worker model loop

The worker uses Effect 4.0.0 with Context.Service and the official @openrouter/sdk 1.4.21. One adapter uses nonstreaming chat.send requests for every review. Requests target https://openrouter.ai/api/v1, reject redirects, and disable SDK diagnostic logging. OPENROUTER_API_TOKEN is the only model credential.

Every model request includes cache_control: { "type": "ephemeral" } to request automatic prompt caching as the conversation grows. This applies to both stages, without a model allowlist. Anthropic uses the default five-minute lifetime. Cache support, lifetime, and minimum prompt length depend on the upstream provider. Each stage retains one session_id for OpenRouter's provider routing.

The worker exposes read, glob, grep, list_skills, load_skill, read_diff, list_diffs, and submit_review. Repository tools retain checkout path and symlink checks. The model cannot call a shell, write files, inspect unrelated host files, load native hooks, or enable network tools. The claimed GitLab token and controller credentials stay in the worker.

submit_review is the only successful final response. The validation tool exposes flat verdict objects with an enum value and an optional reason. The provider-facing schema is derived from the shared contract and avoids object unions. The worker validates every submission with the original shared zod stage schema, which requires a nonempty reason for rejected and duplicate verdicts. Literal tool parameters use singleton enums. Job-specific validation checks the exact verdict count, unique in-range verdict indexes, and unique eligible previous-finding decisions before accepting a submission. These relationship checks run locally and use the same correction attempt as other schema errors; they do not add array-length restrictions to the provider's tool schema. Result assembly repeats the checks before saving publication intent. A submission that is not alone, not valid JSON, or does not match the schema is returned to the model once as a tool result naming the defect and recorded as a submission_rejected diagnostic; a second invalid submission fails the stage. A response that stops with text and no tool call is answered once with a user message asking for submit_review, recorded as a submission_rejected diagnostic with code missing_result; this request is counted separately from the submission correction, and a second text-only stop fails the stage. Refusal, truncated output, or a malformed tool call fails the stage. The worker preserves assistant messages, including reasoning metadata, between tool calls. It requests routes that support the supplied parameters.

Each stage has a 45-minute deadline. Cancellation aborts the active SDK request. When OpenRouter reports an upstream overload, rate limit, or server error, in an HTTP 200 error body or as HTTP 408, 429, 500, 502, 503, or 504, the adapter sends the same request again up to three times, after about 5, 10, and 20 seconds. Each attempt records its reported usage. It does not replay other failed requests, trim conversation history, or impose a model-call or tool-call count limit. Tool replies remain in conversation history, so a review can still exceed a model context limit after its initial request. Local Docker checks exercise live model behavior and controlled tools. Real GitLab acceptance requires the dedicated fixture-project procedure in the local run guide.

Reported usage

The adapter observes each response before executing tools or making the next request, including available usage on error responses. It accumulates request costs and tokens within the stage. The worker serializes observations, appends positive deltas with stable event keys, and advances its baseline after the controller acknowledges the row. Repeated observations do not double-charge.

Every new row records OpenRouter's reported cost, the resolved response model, and priceTableVersion: "openrouter-reported-v1". If the served model ID does not fit the selection contract, the row records the requested model instead. Prompt tokens are clamped at zero when cached and cache-write counts exceed the reported prompt total. The reported cost is recorded in both cases. Missing cost marks usageIncomplete and skips that request's usage row, including its tokens. Later requests with reported costs are still recorded. Missing usage, counter resets, and unconfirmed final usage also mark a gap. No static price table or estimated zero-cost row fills missing observations.

The month and day are computed in the organization timezone at write time. Historical usage rows retain their original accounting versions. The ledger records observed spend; it does not guarantee agreement with the account bill or persistence before the next model call. A crash can leave unobserved usage.

findingDecisions is append-only. The controller updates a finding's current disposition and inserts its decision in one transaction. migrations.backfillFindingDisposition explicitly converts legacy resolved rows to posted, fixed findings with migration provenance. It marks legacy posted rows open. The migration preserves saved review JSON and recoverable publication, and does not invent missing original actors or timestamps. Audit rows that leave disposition unchanged do not invalidate publication. It processes at most 500 matching rows per call. See the migration procedure.

usageEvents contains append-only observed usage deltas. Row counts depend on provider observations; missing usage remains an explicit gap. Each row carries month as yyyy-mm and day as yyyy-mm-dd, both in the org timezone at write time. Rows written before the day column existed get it from the one-off migrations.backfillUsageDay, after which the column becomes required. Nothing reads the ledger by range: the budget gate and the spend page read the rollups below, and per-job spend on the queue and failure pages reads by_job.

usageDaily and usageMonthly are rollups of the ledger. recordUsage adds each new row to both in the same transaction as the insert, after the event key dedupe, so a retried report adds once and the rollups cannot drift from the ledger. Cost is stored as integer micro-dollars in costMicroUsd and converted to dollars on read; the ledger keeps costUsd as reported. reviews is not a sum of rows: a job counts once, on the day and month of its first priced row, recorded on the job as firstUsageDay. A future correction row with supersedes must add the difference to the rollups, not the new amount; nothing writes corrections today. Two workers patching the same rollup row at once is an OCC conflict Convex retries. After a deploy that introduces the rollups, run migrations.backfillUsageRollups until remaining is false; until then the rollups hold only rows written since the deploy, and the spend page and budget gate under-report. The backfill marks each folded row rolledUp and skips rows recordUsage already marked, so it can be rerun or resumed. One exception to the first-row rule: a job in flight at that deploy is counted on the day of its first post-deploy row, and the backfill adds its older rows' amounts without moving the review. This affects at most one job per worker slot, once. See the operator step.

reviewOutcomes holds one small row per done job: its provider, completion time, whether the published label was clean, findings by severity with validator rejects counted apart and duplicates in neither, claim wait, and run time. findingCounts in reviewOutcomes.ts is the one counting rule for these rows, the Reviews table, and the Reviews totals. jobs.complete inserts it in the same transaction that marks the job done, and a done job never leaves that status, so each job has at most one row. Counts are final at completion: later finding decisions change disposition, never severity or a validator reject. admin.overview reads the month's rows through by_completed instead of every done job, whose saved result and diagnostic snapshot made that read grow past Convex's per-query limits. After the deploy that introduces the table, run migrations.backfillReviewOutcomes until remaining is false; until then the overview counts only reviews completed since the deploy. See the operator step. Rows written before duplicates were excluded count them by severity until migrations.recountOutcomeFindings has run; see recount outcome findings.

reviewFailures is the append-only failure ledger. Every job failure, every claim denial, every enqueue-time denial, and every comment delivery that GitLab never accepted appends one row. Rows survive deliberate recovery, which clears the job's own failure fields, and they do not expire with diagnostic events. Detail for a failed job comes from the failure comment's compact snapshot, selected by job and lease generation. Failed delivery rows retain noteId and take their lease generation and snapshot from that original note, even after publication recovery. The worker ID is omitted when the current job belongs to a different lease.

Versioning and releases

FRED follows Semantic Versioning 2.0.0 with one version for the whole repository. The release tag vX.Y.Z is the only source. Package manifests stay at 0.0.0, and nothing commits a version to main.

The public API is what users and operators depend on. A change that breaks any of it is breaking:

ConsumerPublic API
GitLab usersThe 0 FRED token name, adding the FRED bot as reviewer to trigger a review, finding commands, the fred-review::findings and fred-review::clean labels, and the root REVIEW.md contract.
OperatorsEnvironment variables, the setup wizard, the pnpm fred CLI, the Docker stack's services, volumes, and image commands.
DataThe data export archive, fred-export/1, and the transcript file, fred-transcript/1.

Convex tables and the protocol between worker and controller are internal, because one release ships both. At the open-source release, 1.0.0, self-hosters start running schema migrations and may run workers on their own machines, so both join the public API.

Until 1.0.0, every deployment of main is a release. scripts/release.mjs reads the MR titles on main since the newest tag from GitLab's merge commits:

The first release is 0.1.0. Automation never reaches 1.0.0: a maintainer creates the v1.0.0 release by hand on the deployed commit of the open-source release, and later deploys count from it. pnpm fred --version prints a checkout's version: its tag, or the next version as a prerelease such as 0.3.2-dev.4+g1a2b3c4, four changes past v0.3.1, with .dirty appended for uncommitted changes.

Release notes list each title with its author and MR reference under Breaking changes, Features, Fixes, or Other changes, then link the comparison with the previous tag. Fixes include perf and GitLab's revert titles. Reading the merge commits needs no API token.

The deployed version is visible in the admin UI next to the wordmark, on each review in Reviews, in the export's manifest.json, on reviewJobs, usageEvents, and transcripts as fredVersion, and at the end of each summary comment.

The canonical repository and its CI live on FREI's GitLab. Maintainers publish a deployed release to the public mirror on GitHub by hand, as one commit titled chore: publish vX.Y.Z and tagged with the release, so internal MR titles stay internal. git archive builds that tree, so paths marked export-ignore in .gitattributes, FREI's own deployment and archives, stay out. The mirror's history starts at its first published commit. The mirror runs no CI; a maintainer lands an accepted pull request through a GitLab MR, whose pipeline checks it.

Spend and validation limits

The server reads each developer's monthly spend from the usageMonthly rollup, which recordUsage maintains alongside the usageEvents ledger. The budget owner is normally the MR author, or the triggering human for a bot-authored MR. Checks run at enqueue and claim; they do not stop a running review.

New costs use OpenRouter's reported response costs. Historical rows retain their original accounting method. There is no account-bill reconciliation. Failed runs can have incomplete usage, marked on the job. The rollups include all rows without resolving supersedes corrections. The dashboard query in View monthly spend sums the ledger directly; after the rollup backfill it agrees with the server's number to within half a micro-dollar per ledger row, well under a cent, because the rollup rounds each row before summing.

CI uses offline fixtures. Its deployment checks prove controller access and worker connection, not provider compatibility or successful review publication. Agents may run explicit live provider checks through the isolated local Docker command. CI remains synthetic.

Environment

pnpm run setup runs the interactive setup wizard. It labels required and optional inputs, captures secrets without echoing them, and retains saved values on Enter. It generates FRED_TOKEN_KEY unless one is saved and explains connecting each project's 0 FRED token in the admin UI and adding its webhook. Final worker settings are checked against the actual worker configuration schema without starting services. Fixture startup remains disabled if its explicit live opt-in is skipped.

The wizard saves deployment credentials in apps/controller/.env.local, controller runtime values in apps/controller/.env.runtime, worker values in apps/worker/.env, and local Docker settings in apps/controller/self-hosted/.env. Files have mode 0600. Existing unrelated values are retained; file formatting is normalized. Setup values must be single-line and cannot contain single quotes.

The controller runtime file is a local copy, not an automatic Convex env source. After a separate target-specific confirmation, the wizard applies those values to the self-hosted controller and reads them back. Admin and provider keys are excluded from that update. Applying refuses to replace a different FRED_TOKEN_KEY already on the controller, because the stored project tokens would become unreadable. Setup makes no GitLab requests, does not call model APIs, and does not start reviews.
