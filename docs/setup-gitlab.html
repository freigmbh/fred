How to set up GitLab for the AI review service

How-to. Each project reviews through its own FRED bot, the bot user of a project access token named 0 FRED. A project Maintainer creates the token and the webhook; the FRED admin connects the token in the admin UI. For configuration details, read the reference.

Create the 0 FRED project access token

  1. As project Maintainer, open the project's Settings > Access tokens and add a new token.
  2. Name it 0 FRED. GitLab shows the token's bot user under this name, and the leading 0 sorts it first in reviewer pickers.
  3. Select the Developer role or higher and the api scope. Choose an expiry date that suits your rotation policy.
  4. Create the token and copy its value. GitLab shows it only once.

Create a project access token, not a personal or group token. FRED refuses a token that belongs to a person or reaches more than one project.

Connect the project in the admin UI

  1. Log in to the FRED admin UI and open Projects. Click Connect.
  2. In the Setup tab, paste the token.
  3. The line below the token names the review pipeline Connect saves, starting from the default. To change it, click Change and choose the model and effort for detection and validation in the Review tab. If the model list is empty, click Refresh under the panes.
  4. Back in Setup, click Connect. FRED checks the token with GitLab, finds the project from the token, creates any missing review labels, stores the token sealed, and sets FRED's face as the bot's avatar.

The project appears in the list. Its Setup tab shows the token's bot user, role, expiry, last check, and scopes. If the check fails, the form names the problem, such as a missing api scope or a role below Developer. Fix the token in GitLab and connect again.

FRED sets these scoped labels. Connecting creates the missing ones as project labels; an existing project or group label with the same name also works. Keep their names unchanged. The worker never creates labels.

LabelSet when
fred-review::cleanFRED has no posted, open blocking or should-fix finding.
fred-review::findingsFRED has at least one posted, open blocking or should-fix finding.

Scoped labels with the same prefix replace each other, so an MR carries one FRED label.

Add a webhook to the project

  1. Open the project's Settings, then Webhooks.
  2. Set the URL to the controller's site origin plus /webhook/gitlab. Use an address GitLab can reach over the company network. A localhost address works only when GitLab runs on that same host.
  3. Enter the existing GITLAB_WEBHOOK_SECRET value as the secret token. Use the same URL and secret for every project.
  4. Tick Merge request events and Comments. Comment events deliver finding commands.
  5. Enable SSL verification when the controller sits behind TLS.
  6. Save the webhook. Configure only one FRED webhook per project.

For an existing FRED webhook, enable Comments on that webhook and save it. Do not create a second webhook. Verify command delivery with a dedicated fixture MR.

A project needs both the connected token and the webhook. Until the project is connected, its webhook deliveries return {"ignored":true,"reason":"project not connected to FRED"}.

Request a review

Add 0 FRED as reviewer on a merge request. FRED reviews again on every push while it stays assigned. On GitLab versions that emit a re-request webhook, re-request the review to review the same commit again. After a failure, remove and re-add 0 FRED.

FRED reviews an MR from a fork only when the project token can read the source project. A project access token belongs to its own project, so MRs from forks in other projects are generally not reviewable.

Rotate or replace the token

The Projects page warns 30 days before the token expires and marks it failed once it has expired or GitLab rejects it. FRED checks every token every six hours; Check checks one immediately.

  1. In GitLab, use Rotate on the 0 FRED token. Rotation keeps the same bot user.
  2. In the admin UI, select the project, open Setup, click Replace, and paste the new value. A token of another project is refused.

If you create a brand-new token instead, GitLab creates a new bot user. FRED remembers every former bot user of the project, so earlier FRED discussions and summaries remain FRED's. Reviewers must add the new 0 FRED user; the old one no longer triggers reviews. Revoke the old token after replacing it.

Stop reviews for a project

  1. In the admin UI, select the project, open Setup, click Disconnect, then Confirm disconnect. FRED deletes the stored token.
  2. In GitLab, disable the project's FRED webhook and revoke the 0 FRED token.

After disconnecting, new review requests are ignored. Reviews and finding commands already queued fail when a worker picks them up, and FRED cannot post their failure comments. Let running reviews finish before disconnecting. Review history, the pipeline, and spend stay. To enable reviews again, connect a new token and re-enable the webhook, then request the review again.

Verify with one fixture MR

Run this check manually against the local controller and a dedicated fixture project, as described in the local run guide. Starting reviews spends provider budget and posts to GitLab.

  1. Connect the fixture project with its 0 FRED token in the local admin UI.
  2. Open an MR in the fixture project and add 0 FRED as reviewer.
  3. Check for a summary comment that starts with FRED review and a fred-review:: label. If nothing appears, inspect the project webhook deliveries, then the controller and worker logs.
  4. Verify dismissal and undo with the finding-command check. Resolving a GitLab discussion alone does not change its finding disposition or label.

Optional: add review instructions to a repo

To steer both review stages, add REVIEW.md at the repo root. Write the project review rules and name any repo skills to follow. The reviewer can discover every repo SKILL.md and read its reference files. It also reads root AGENTS.md, otherwise CLAUDE.md, for general conventions. Missing review rules produce a feature tip; a missing requested skill produces a hint and review continues. These files cannot enable shell execution or expand sandbox permissions.
